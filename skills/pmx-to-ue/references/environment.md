# 环境与执行

先确定三个独立路径：工作流仓库、目标 `.uproject`、源 PMX 包。不要从当前目录推断它们相同。移动到新电脑后更新角色配置的绝对路径；通用代码不改。复制整个工作流，不需要任何历史实验工程。

以用户指定工程及其本地约定为准，默认在该工程内使用独立资产版本，不自行创建新的 UE 测试工程。下列独立打包/空白项目验证仅用于明确的插件分发或跨工程测试。宿主已经提供原生接口时复用其模块，避免重复加载同名反射类型。

1. `pmx4ue.py init` 生成角色 work order；需要真实 PMX、现有目标工程和按米计的 PMX 单位比例。`doctor` 只检查路径，不检查插件是否已编译。
2. Blender 3.6 配置可导入 `mmd_tools` 的环境。导入在独立后台进程完成，Blender 异常使用 `--python-exit-code 1` 返回失败。版本不符先做只读 API 探针，不自动下载安装。
3. `RunUAT BuildPlugin` 先在独立 HostProject 编译；本包的 Runtime 节点与 Editor 工具已经分离，Editor 依赖不会进入 Shipping Runtime。参照 README 的命令。
4. `maintenance/verify_plugin.py --engine <UE根> --plugin <打包输出> --output <新目录>` 创建空白验证工程并检查 Python API，不修改现有工程。源码/打包插件安装器拒绝覆盖已有目录；更新由 agent 审阅 diff 后单独处理。
5. 不要把本插件装进已含 `FAnimNode_PmxFilteredRigidBody` 等同名原生类型的工程。`ue_bridge.py` 检查可用 provider；类名兼容旧宿主不意味着需要该宿主的工程或内容。

## 运行记录

`run --stage <名称>` 只预览；加 `--execute` 才运行。可用阶段见 `--help`。每次记录输入文件哈希、代码哈希、完整配置、输出哈希、进程返回状态和日志。输出存在时不重写；失败留下现场，由 agent 检查后选择新版本或明确的清理范围。

`status` 检测记录中输入/输出文件变化；材质预览还记录截图及已枚举的项目材质/网格依赖文件指纹。但它**不是完整依赖调度器**：不检查编辑器未保存修改，也不覆盖所有阶段的 UE 依赖或自动批准过期结果。改配置、脚本、贴图或 UE 资产后由 agent 判断需要重跑哪些阶段。`Saved/PMX4UE/.agent.lock` 防止多个运行器同时写工程；异常残留锁先核实进程，不盲目删锁。

运行器不启用 ForceMemoryCache、不改 RHI/质量、不锁 60 FPS。性能阶段启动自己拥有的临时编辑器，只关闭这一实例；不用用户当前场景。Windows 构建前阅读下面的日志与沙箱规则；这是 agent 操作规程，不代表运行器已实现自动诊断或权限审批。

## Windows 构建：UBT 跟踪日志与沙箱

### 构建前

确定实际 UE 版本、构建入口、引擎选用的 dotnet 路径和宿主允许写入的范围。不能因为工程目录可写，就认为构建所需的用户目录也可写。提前记录完整命令、工作目录和项目内本次日志位置；工程输出隔离不等于 UBT 共享跟踪日志隔离。编译串行执行，不为探测权限反复启动 UBT。

已检查的 UE 5.8 源码中，`UnrealBuildTool.Main` 在解析全局命令行参数前创建并轮换 `Trace.uba`，这一步还在其后续主 try/catch 之前。安装版、非 BuildMachine 路径通常为 `%LOCALAPPDATA%/UnrealBuildTool/Trace.uba`。因此 `-Log=<工程日志路径>` 只重定向普通日志，不能修复启动早期的 Trace 轮换拒绝访问；不要把 `-WaitMutex` 当作这一早期步骤的串行保护。

核对目标安装的相对源码位置（其它 UE 版本需重新确认）：

- `Engine/Source/Programs/UnrealBuildTool/UnrealBuildTool.cs`：`Main`、`Trace.uba`、`Log.BackupLogFile` 与命令行解析顺序。
- `Engine/Source/Programs/Shared/EpicGames.Build/Unreal.cs`：`EngineProgramSavedDirectory` 和用户设置目录。
- `Engine/Source/Programs/Shared/EpicGames.Core/Logging/Log.cs`：`BackupLogFile` 中旧备份删除及轮换操作。

不要通过虚构环境变量、改变全局 AppData、伪造 `-Session` 或关闭诊断来绕过这一问题。若版本确实提供跟踪路径配置，先核实生效时序；仅改变普通日志不能算修复。

### 出现异常后

1. **保留证据，停止相同条件重试。** `0xe0434352` 本身不能定位根因。收集实际异常类型、消息、调用堆栈、拒绝访问的精确路径、命令、退出码和日志；必要时读取同一时间的 Windows `.NET Runtime` / Application Error 事件。此阶段失败不是 C++ 编译错误，也不证明后续 C++ 必然可编译。
2. **区分沙箱、文件权限和占用。** 只读检查该文件及父目录 ACL、文件属性和相关构建进程；需要时检查文件占用。当前用户有完全控制权，不代表受限沙箱令牌有同等权限；独占只读打开成功也不能证明允许写入、重命名或删除。没有 dotnet 进程也不足以单独排除其它占用者。
3. **有沙箱限制证据才申请权限。** 使用当前宿主的正常审批机制，为原构建命令申请必要访问，以当前用户身份执行。此举不等于 Windows 管理员提升，不得自行绕过宿主拒绝的授权。无审批能力或审批未获准时记录阻碍并交接，不循环尝试。
4. **条件修复后只重试一次。** 保持同一构建命令、代码和配置，串行执行；记录获批权限范围、退出码和实际普通日志/Trace 位置。相同异常再次出现就停止，交付原始证据；不能靠改文件名或再次启动新命令重置重试次数。若出现不同错误，应重新分类，不沿用沙箱结论。
5. **不是沙箱问题则按证据处理。** 普通用户环境同样失败时，定位精确 ACL、只读或占用原因；权限修改、移动旧文件、关闭进程等操作须明确目标及授权。不得自动重装 .NET、扩大系统 ACL、删除整个共享日志目录、批量结束 dotnet 或默认管理员运行。

成功退出只说明该次构建通过。随后仍需验证插件加载和实际接口，材质、骨骼、IK、物理分别验收。将故障与重试记录写入工作单关联的 decision/handoff，而不是只留在聊天中。

### 已确认案例及证据边界

用户转述的独立工程 JiangYu 测试：旧跟踪备份文件对当前用户完全控制，但沙箱身份只有读取权限；文件无只读属性，独占只读打开成功，当时未发现 dotnet 进程。通过正常权限审批后，以普通用户身份执行唯一一次原构建，18 个编译/链接动作通过、退出码 0，Trace 写入用户 AppData，工程日志位于 `Saved/PMX4UE/JiangYu/v1`。

这是用户提供的另一 agent 诊断与构建结果，本仓库未收录该次原始日志，也未在此次文档更新中复跑。结合权限差异和同命令获批后成功，支持该案例的沙箱写入限制结论；不能据此认定所有 dotnet 弹窗同因，或宣称该角色后续导入与物理验收已通过。新工程使用自身工作单路径，不照抄案例目录。

## Blender FBX 版本适配

已只读核对安装版 3.6 与 5.2 的 `io_scene_fbx/data_types.py`：3.6 的 BOOL 使用 `C`，5.2 的 BOOL 使用 `B`、CHAR 使用 `C`。不能仅把编码表改为新版本常量，否则旧版会回退。`blender_fbx_bind.py` 现在从当前 codec 的类型定义和实际 encoder 方法建立映射（含 INT8），未知/缺失方法明确失败。导出后仍逐字段回读验证，报告记录 codec 路径/映射；这不等于 Blender 5.2 的 mmd_tools 导入及全链已经兼容。新版本适配须在独立新输出跑完整 FBX 回读，再查 UE 绑定告警。

## 文件管理

建议角色工作单、决策/交接记录、经过审核的 rig/physics/material 配置进入该仓库 Git。源资产、绝对机器路径、生成物按团队权限选择是否提交；不要打包第三方模型。`.local/`、`runs/`、插件二进制/中间文件默认忽略。脚本库与角色配置可以独立演进，升级需保留旧成功版本。
