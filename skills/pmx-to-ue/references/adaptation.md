# Agent 扩展、实验与交接

## 配置、脚本、引擎能力分别处理

| 发现 | 优先处理 |
|---|---|
| 骨名/材质槽/group 不同 | 改角色配置，保留共享工具 |
| 某 PMX 原始语义现有工具未支持 | 写探针确认数据，增添小适配器和失败/成功用例 |
| UE 版本 Python/C++ API 变化 | 检查本机源码，做显式版本适配，独立编译与加载验证 |
| 视觉风格没有客观唯一答案 | 给出对照及代价，请用户选关键方向，其余 agent 完成 |
| 现有脚本本身实现错了 | 在新工作流仓库修正并回归，不回写历史工程工具 |

`templates/special-requirement.md` 是可直接交给另一个 agent 的任务合同，不是让它猜上一段对话。给原始证据、目标不变量、允许修改范围、失败用例和验收要求，允许它参考当前版本文档并提出更好的实现。

## 每次实验的小闭环

1. 在当前角色目录创建 decision 记录，列明观察及可证伪假设。
2. 选择最少有区分度的 A/B；如果只是配置问题，不先改 C++。
3. 新脚本或修改后的脚本先跑纯逻辑测试，再做 Blender/UE 真实环境验证。不能只验证字符串包含某值。
4. 记录效果与代价，失败也保留原因。成功后将可泛化部分并入公共工具，角色专属部分留在配置。
5. 更新受影响说明与版本；Git 一个提交对应一个可解释变化。不要创建空目录或为了架构扩展性制造未实现的插件接口。

可以由 agent 新增 runner 阶段，或直接执行现有工具；只要操作在用户范围内、输出隔离、可重复即可。reviewed 标记不能代替证据，检查器也不是永远不能改变的定律；修改检查标准时要说明原标准为何不适用并补充更准确的验证。

## 接手输入

另一 agent 至少需要：工作单和本机路径、最新 Git revision、源 PMX/纹理访问方式、导出/UE 资产路径、最新日志/报告、已经确认的效果、尚未解决的问题、下个最小动作。使用 `templates/handoff.md`。没有前一段聊天也应能恢复工作。

并行分析适合材质盘点、骨架报告阅读、物理语义核对；UE 资产写入和编译更新应串行。不要为了并行自动创建用户可见的新任务，遵守当前宿主的委派规则。
